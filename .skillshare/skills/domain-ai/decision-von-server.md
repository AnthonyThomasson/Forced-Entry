# AI · Decision · The Von server launcher

`scenes/ai/decision/decision_server_launcher.gd` (a root node of `main.tscn`), with `server_probe.gd` (the readiness probe) and `server_output.gd` (the boot script's output). The transport and the test seam are `decision-von.md`'s.

## Starting and stopping

A dev convenience: starts a local `von serve` when the game runs **from the editor** (never in exported builds) and stops it on exit. It runs the boot script of the current OS start-only (`DecisionServerLauncher.boot_command`): `tools/von/boot.sh` on a Mac, run as `/bin/bash boot.sh` (no exec bit needed, which a ZIP download loses; the script ends in `exec`, so the bash pid becomes the server); `tools/von/boot.ps1` through Windows PowerShell 5.1 with `-ExecutionPolicy Bypass` on Windows. The script finds the Von install in the per-user Forced-Entry home itself (ADR 0014); there is no path setting. `probe_only` (the test gate's, with `GAME_TEST_VON_PORT`) never starts a server. Stopping is `OS.kill` of the script's pid on both OSes: on a Mac the script has become the server (`exec`), on Windows `boot.ps1` holds it in a kill-on-close job. A server that can still **decide** on `port` is reused and left running. The port, host, path and model come from `NpcDecisionTuning`'s constants (`SERVER_PORT`, `SERVER_HOST`, `SERVER_PATH`, `MODEL`), the same ones the NPCs' `server_url` and `model` default to. Every NPC shares the one server. Output goes to `user://von_server.log` and echoes as `[von] …` lines (`ServerOutput`); on exit it joins its readers for 1.5 s at most and leaves one whose pipe stays open (`reap`), so the game's close never hangs on it.

## No setup, no port

Every case resolves `false`, leaves the setup window usable within `ready_timeout` (180 s, from scene load) and the NPCs holding steady, with a warning naming cause and fix (also `launcher.problem`; the tests `von_setup_missing_holds_steady`, `von_port_taken_by_another_server`):

- **Setup missing or broken** (no Python, a half-finished bootstrap after a pip failure or an offline first run: no venv, base Python gone, von-sdk or weights missing): the boot script exits 3 with `von: <cause>. Fix: <bootstrap command>`. The launcher reads its stdout and stderr (a thread each) and sees it end at once, so the warning is `[von] No decision server: von: <cause>. Fix: <command>. NPCs hold steady.` (`exit_warning`). Fix: run the bootstrap (`tools/setup/bootstrap.sh`; Windows `powershell -ExecutionPolicy Bypass -File tools\setup\bootstrap.ps1`), start the game again.
- **Port held by something that is not Von:** an HTTP server that cannot decide is not replaced; it warns `up but cannot decide (HTTP n)` and what to do (stop it: an old Von with `tools/von_stop.sh <game pid>`). A listener that accepts and never answers (a hung program, no HTTP) is not launched over either, since our server could not bind after loading the whole model: the probes run out, or the deadline passes, and it warns `Port N is held by something that does not answer a decision` (test `von_port_held_silent`). A server of ours whose port a deciding Von already serves is reused.
- A closed port is told from a server by a TCP connect (`_port_open`, 3 s), not the HTTP request: on Windows that waits out its whole 15 s timeout. **One deadline**, scene load plus `ready_timeout` (`_probe.ready_deadline_ms`), bounds every path (each request's timeout is cut to what is left), so none outlasts it.

**Background QoS (macOS).** `background_qos` (`@export`, default on): once the server WE launched answers its readiness probe, `_announce_ready` runs `/usr/sbin/taskpolicy -b -p <pid>` on it (`qos_args(pid, os_name, background)`, a pure static the `von_launch_command_suite` tests: empty off macOS, with the flag off, or with no pid, i.e. a reused server). Why: PyTorch on CPU bursts to 500 to 1000% CPU at fight start and starved the game (frames of 255 to 335 ms for about 15 s; macOS, 2026-11-12); background QoS keeps the server on the efficiency cores and cut the first 5 s to about 57 ms a frame, then 16 to 19 ms. `renice` and the OMP / MKL / torch thread variables did not help. It is applied after the first answer, not at launch: a server launched under `taskpolicy -b` took about 57 s to its first shot against 29 to 37 s, eating `ready_timeout`. A non-zero `taskpolicy` exit (70 dead pid, -1 could not start) logs `[von] QoS not applied (exit N)` (`qos_failure_line(code)`). The cost: Von answers slower for the rest of the run. The test gate (`TestVonGate`) sets `background_qos = false` (its asks are capped at 10 s); coverage's `runner.py` starts its own server untouched.

## Scene load and the probe

It runs at **scene load**, while the setup window is open, so the server gets its whole boot time before any NPC exists:

- A probe whose port is **closed** launches at once; the retries (`probe_attempts`) pay off only for a probe that **times out** (a slow server worth reusing).
- The probe **POSTs a real decision** instead of checking `GET /`, because an **orphaned server is worse than an absent one**: a `von serve` left by a hard-killed run has a dead stdout pipe, so its weight fetch dies on `EPIPE` for good while it keeps serving HTTP, and every decision comes back `422`. Asking it to decide catches that and resolves `false` with the server's `detail`. It doubles as a warm-up. After launching, the launcher polls its own server until the first answer and prints `[von] Decision server live on port N, Xs after scene load`: ready means a LIVE brain.

**`resolved(live)` + `is_resolved()`** is the gate contract (interface 22). It fires EXACTLY once, and every terminal path reaches `_resolve()`: server answered (`true`), or none is coming (`false`: exported build, `probe_only`, a missing or broken setup, a failed spawn, `ready_timeout`, a server up that cannot decide). Any new terminal path MUST resolve, or the setup window hangs. `main.gd` awaits it before `start_match` so no NPC makes its first decision against a cold server (a run with no server still starts, NPCs holding steady). Main checks `is_resolved()` *before* awaiting: the exported-build path resolves synchronously in `_ready()` and children are readied before their parent.

## Live test runs

**Preflight (`--require-von`, `--record-von`).** Before any engine starts, `tools/run_tests.sh` runs `tools/von/boot.sh --check` and stops (exit 1, no test run) when Von cannot start, with one `von: <cause>. Fix: <command>` line: no Von venv, the venv's base Python gone (`pyvenv.cfg` `home =`: a package manager removed the Python it was built on), its Python not running, von-sdk or the weights missing, or `von --version` failing. The fix is the bootstrap command of the OS (the Windows one printed even from Git Bash), which rebuilds the venv under the Von home and resumes the weights. `--include-von` skips instead; `GAME_TEST_VON_PORT` (no server is started) skips the check. By hand: `tools/von/boot.sh --check`, `boot.ps1 -Check`.

Killing a Bash-launched Godot (`godot-run`) is a hard kill: `_exit_tree` does not run and the spawned Von server is orphaned on port 8000. Stop the server BEFORE the kill with `tools/von_stop.sh <game pid>` (only the server under that game, whose own pid it takes, not a wrapper's; another worktree's keeps running). A normal test run replays and starts no server; only live, recording and live-only runs do.
